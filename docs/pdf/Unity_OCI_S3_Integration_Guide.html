Unity → OCI S3
Credential Lifecycle Manager

How an authenticated Unity connector receives a scoped Customer Secret Key, accesses its bucket, and releases the lease.

Main integration endpoint
POST https://axcl6ctgxzrva4pjnkhxflibum.apigateway.us-ashburn-1.oci.customer-oci.com/v1/leases

Unity sends an OAuth access token and an approved profile. The backend chooses the available service user; Unity does not supply a user OCID.

End-to-end flow

1. Unity connector obtains an access tokenOCI Identity Domains • client_credentials grant • cache until expiry
↓
2. Unity calls API GatewayPOST /v1/leases • Bearer token • profile • unique Idempotency-Key
↓
3. Gateway and backend authorize the requestGateway validates JWT; backend checks identity-to-profile mapping and scopes
↓
4. Backend creates and records the keyReserve service user → OCI IAM creates key → ADB records key, expiry and cleanup intent
↓
5. Credentials return immediatelyHTTP 201 / SCHEDULE_PENDING • access key ID + secret access key
↓
6. Background setup completesConfirm expiration schedule → store bounded replay response in Vault → ACTIVE
↓
7. Unity uses S3, then revokesSign S3 requests with the key pair; DELETE lease and confirm REVOKED

“Immediately” means after IAM creation and durable recording, not zero latency. ADB reservation and key recording remain synchronous.

01 · IDENTITY AND AUTHORIZATION

Onboard the connector

The demo UI uses human OIDC sign-in, then a server-side connector access token. A real Unity wrapper obtains its own service token and calls the API directly. It does not use the browser’s /auth/* or /connector/* routes.

Operator setup

  1. Create a dedicated confidential OAuth client in the OCI Identity Domain and enable client_credentials.
  2. Approve the required API scopes and configure the backend’s connector identity-to-profile mapping.
  3. Store the client secret in a secret manager. The demo client does not automatically authorize a new Unity client.

Obtain the access token

Token endpoint:

https://idcs-1ee8a5696b814af291e90b1adc2fe166.identity.oraclecloud.com/oauth2/v1/token

Use HTTP Basic authentication with client_id and client_secret, and a form-encoded body:

grant_type=client_credentials
scope=https://axcl6ctgxzrva4pjnkhxflibum.apigateway.us-ashburn-1.oci.customer-oci.com/lifecycle/sales-read

Use the scope ending in sales-write when approved. Cache access_token using expires_in; refresh before expiry. The demo service token lifetime is currently up to 600 seconds.

How service-user selection works

ProfileBucket / permissionsConcurrent leases
sales-readlcm-live-v2-sales
LIST, GET		2
sales-writelcm-live-v2-sales
LIST, GET, PUT		2

The backend intersects the connector’s approved profiles with its token scopes, verifies the requested profile, then reserves an available, non-quarantined service user from that profile’s pool. No DELETE permission is granted.

Profiles are backend configuration. OAuth scopes permit requesting profiles; the service user’s group membership and bucket-restricted IAM policies enforce its actual S3 access. The backend does not interpret arbitrary IAM policies dynamically on every request.

Identity boundary

The API identifies the connector application. Per-end-user Unity permissions require wrapper-side enforcement or an explicitly designed user mapping. A valid token alone does not authorize every bucket or profile.

Use the OAuth access token—not an ID token, OCI Console Auth Token, SSH key, or OCI API signing key—as the Bearer token.

02 · REQUEST AND USE CREDENTIALS

Integrate the lease API

All API paths below are relative to the base URL on page 1. Start with GET /v1/config using the Bearer token to discover authorized profiles, their buckets, and TTL bounds.

Create a lease

POST /v1/leases
Authorization: Bearer <access_token>
Content-Type: application/json
Idempotency-Key: <persisted UUID for this intended lease>

{
  "scope_profile": "sales-read",
  "ttl_seconds": 300,
  "delivery_mode": "immediate",
  "client_request_id": "unity-query-123"
}

HTTP 201 returns a new credential pair. HTTP 200 is a replay. Example response fields (placeholders only):

{
  "lease_id": "<lease UUID>",
  "status": "SCHEDULE_PENDING",
  "access_key_id": "<issued access key>",
  "secret_access_key": "<issued secret>",
  "endpoint": "<returned OCI S3 endpoint>",
  "region": "us-ashburn-1",
  "scope_profile": "sales-read",
  "expires_at": "<UTC timestamp>",
  "expiry_mode": "managed_key_deletion"
}

TTL is 300–3600 seconds, default 900, measured from IAM key creation. Explicitly send delivery_mode: immediate; the default confirmed waits for scheduling and Vault retry storage.

Configure the S3 client

SettingValue
Endpoint / regionUse endpoint and region returned by the API
CredentialsUse access_key_id and secret_access_key; no session token
ProtocolAWS Signature V4; path-style addressing
BucketUse the selected profile’s bucket from GET /v1/config

The JWT authenticates lifecycle API calls. The issued key pair signs S3 calls. New keys can require propagation before S3 accepts them; use bounded retries without extending the lease deadline.

Keep secrets in memory. Do not log Authorization headers or raw credential responses. The published Python example uses confirmed delivery by default; add delivery_mode: immediate to use the fast response path.

03 · STATUS, RETRIES AND CLEANUP

Manage the full lifecycle

OperationEndpoint
Discover approved profilesGET /v1/config
Create or replay credentialsPOST /v1/leases
Inspect a leaseGET /v1/leases/{lease_id}
Inspect request progressGET /v1/lease-requests/{idempotency-key-UUID}
Revoke earlyDELETE /v1/leases/{lease_id}
List recent owned leasesGET /v1/leases

Understand the stages

Status / phaseMeaning
PREPARINGService user reservation and key creation
SCHEDULE_PENDING / CONFIRMING_SCHEDULEKey recorded; expiration schedule confirmation pending
SCHEDULE_PENDING / PREPARING_REPLAYSchedule confirmed; bounded Vault retry storage pending
ACTIVEScheduling and retry storage complete
REVOKE_PENDING → REVOKEDDeletion requested → key absence confirmed and cleanup recorded

Metadata and progress endpoints never return the secret. The UI shows committed stages beneath Status and in the credential panel; brief stages may fall between refreshes.

Revoke when finished

Call DELETE with a valid token for the same connector owner and authorized profile. HTTP 202 means revocation was requested; 204 means already revoked. Poll GET until REVOKED.

Cleanup deletes the owned IAM key, removes its schedule and replay data, updates ADB, and frees the pool slot. The service user and bucket data remain. Expiration scheduling and independent reconciliation provide fallbacks; failed cleanup stays pending for retry.

Handle retries safely

ResponseAction
401Refresh the token; check issuer/audience if it persists
403Check connector mapping, scope and ownership
409 ISSUANCE_PENDINGBack off; retry with the same UUID and identical body
409 IDEMPOTENCY_CONFLICTThe same UUID was reused with a different body; correct the caller
409 CREDENTIALS_NOT_REPLAYABLEInspect/revoke the original lease before deliberate replacement
429Honor Retry-After; bound concurrency to available pool capacity
503 / uncertain network resultPreserve the UUID; inspect progress/lease before retrying
Immediate-delivery tradeoff

The key is exposed before schedule and Vault confirmation. Background failure triggers revocation. Process loss can make replay unavailable; stale pending setup is revoked by reconciliation. Stop using the key at expires_at. There is no lease-extension endpoint.

04 · TESTING AND ALTERNATIVE HTTP ACCESS

Verify the integration

Manual Postman test

  1. Use POST to the full /v1/leases URL on page 1.
  2. Select Authorization → Bearer Token and paste a valid, single-line access token.
  3. Add Content-Type: application/json and a persisted UUID Idempotency-Key.
  4. Use the JSON body on page 3 with delivery_mode: immediate, then Send.
  5. Measure the 201 response time. Keep the same UUID when retrying an uncertain request; 200 is replay, not new minting.
  6. Revoke the test lease and confirm REVOKED.

If Postman reports an HTTP/2 stream error, try request Settings → HTTP version → HTTP/1.x. Remove duplicate headers and let Postman set Host and Content-Length.

Run from existing OCI compute

From Terminal in the project folder, use the existing DemoBastion SSH configuration:

ssh -F .local/ssh-config lcm-live \
  'sudo /opt/lcm-live/venv/bin/python - --remote --samples 1' \
  < scripts/oci_issuance_benchmark.py

The API call and monotonic timer run on OCI. Look for credential_response_seconds. OAuth token acquisition and SSH are before timing; background completion and revocation are afterward. Change samples to 5 for a small multi-request run.

MeasurementObserved baseline

The recorded baseline used the demo backend VM as the client. Five samples are preliminary, not a production p95 or latency guarantee. The test does not isolate the IAM call or measure S3 propagation.

Alternative: request a bucket operation directly

POST /v1/bucket-operations
Authorization: Bearer <access_token>
Content-Type: application/json

{"bucket":"lcm-live-v2-sales","operation":"LIST","limit":20}

This path selects an already-authorized profile by bucket and operation and uses the backend workload identity. It creates no service-user lease or SK. LIST supports up to 100 objects; GET/PUT support up to 512 KiB. It is a custom HTTP API, not a native S3 endpoint.

Acceptance boundary and references

Actual Unity engine integration remains outstanding. Customer Secret Keys have no native STS expiry; S3 enforcement can lag IAM deletion. This demo is not production-ready.
